# 角色化文章素材卡与质量提升方案 V1

状态：V1 已实施并完成非发布真实 AI 验证（2026-07-20）。

## 1. 目标

在**不改变现有 WordPress / CMS 上传格式、Markdown/HTML、Meta、slug、图片与内链输出结构**的前提下，降低文章模板化程度，提高内容的具体性、站点匹配度与事实可靠性。

当前问题不是发布格式，而是生成前提供给模型的站点、事实和文章差异信息不足，导致不同主题容易复用相似的结构、开头、FAQ 与 CTA。

## 2. 核心决策

新增“文章素材卡”（Generation Context）。每次正式生成前建立一份结构化、可审计的素材卡；Brief、大纲、正文和 QA 全部读取同一份素材卡，不能在不同阶段重新猜测文章定位。

素材卡按站点角色分为两类：

### 2.1 主站商业内容卡

适用于 `is_main=true` 的主站。

- 必须包含已确认的产品页或分类页；
- 必须包含可验证的产品事实、适用场景和转化目标 URL；
- 文章必须服务一个明确的商业承接页；
- 产品价格、库存、规格、配送、限制与合规声明只能使用已确认资料。

### 2.2 内容站编辑内容卡

适用于专门发布文章的博客/WP 站点。

- 必须包含站点定位、目标读者、主题边界、用户问题与市场/语言；
- 必须包含 SERP 缺口、允许引用的来源和本站内链方向；
- 不强制绑定产品页、分类页或购买 CTA；
- 是否允许自然链接到主站，由站点级链接策略决定；不得为了转化硬塞外链；
- 高风险事实没有允许来源时，文章进入 `hold` 或草稿，不得正式发布。

## 3. 素材卡字段

```text
site_role                 main | content
site_profile              定位、受众、语气、主题范围、禁写边界
keyword_and_intent        关键词、搜索意图、市场、语言、用户问题
article_goal              文章类型、独有角度、必须回答的问题
target_asset              主站商业承接页；内容站可为空
link_policy               本站内链规则、允许的跨站链接规则
serp_snapshot             固定的 SERP 快照 ID、市场、语言、竞品缺口
facts_and_sources         已确认事实、可用来源、需引用的声明
required_modules          按文章类型决定的章节、FAQ、CTA、表格、图片要求
forbidden_claims          不可编造的产品、健康、法规、运输等主张
context_version / hash    用于重试、缓存和审计
```

FAQ、CTA、图片、表格和引用不再对每篇文章一刀切；它们由 `site_role`、文章类型、用户问题及素材卡决定。

## 4. 明确不改的边界

- 不改现有 WordPress / CMS 发布器、远端回读和幂等发布逻辑；
- 不改现有 Markdown/HTML、Meta、slug、图片及内链的上传字段与输出结构；
- 不打开 `exdivo` 的普通博客策略开关；
- 不把内容站伪装成产品站，不强制所有文章导向主站；
- 不在第一阶段新增数据库表；素材卡先保存在现有任务决策记录与 `articles.article_parts` JSON 中。

现有输出协议存在 YAML 与非 YAML 规则并存的问题。实施时以当前发布器可稳定消费的协议为唯一标准；这属于规则对齐，不改变远端可见的发布格式。

## 5. 修改范围

| 位置 | 计划修改 |
|---|---|
| `app/services/generation_context_service.py`（新增） | 构建、校验、哈希与冻结角色化素材卡。 |
| `app/services/article_generation_service.py` | 在 Brief 前创建/读取素材卡，并传给 Brief、大纲、正文与 QA。 |
| `app/services/brief_service.py` | 接收素材卡；Brief 缓存键加入素材卡版本/哈希。 |
| `workflows/seo-standard.json` | 增加主站/内容站的内容规则；不改变发布格式规则。 |
| `app/services/article_service.py` | 在既有 `article_parts` 中保存素材卡快照和版本信息。 |
| `tests/` | 增加素材卡、角色化 Prompt、事实门禁和 QA 的回归测试。 |

第一阶段不修改前端；若需要人工查看素材卡、证据缺口或 QA 原因，再单独增加只读展示。

## 6. QA 增量

保留现有格式 QA，并增加以下内容 QA：

- 是否回答素材卡指定的用户问题；
- 是否符合站点定位、主题边界与语气；
- 主站是否使用批准的商业承接页；
- 内容站是否遵守本站内链和跨站链接策略；
- 高风险事实是否来自允许来源；
- 是否缺少素材卡要求的独有信息，或存在明显通用套话。

小型问题可进行最多两次局部修复；仍未通过则保留草稿并转人工，不自动发布。

## 7. 实施顺序与验收

1. 新增素材卡服务和单元测试；
2. 接入正式文章生成链路，确保 Brief、大纲、正文和 QA 使用同一快照；
3. 接入角色化规则和内容 QA；
4. 用主站与内容站各至少两篇草稿进行真实 AI 生成对比；
5. 验收上传格式、发布预检与远端回读没有回归；
6. 人工确认文章在结构、开头、CTA、事实和内链上不再趋同后，再考虑接入 Knowledge/Source Pack 的下一阶段。

验收要求：

- 不同站点画像生成的 Prompt 不得相同；
- 内容站没有产品页时仍可生成合规文章；
- 主站文章缺少商业承接页时不得生成正式草稿；
- 无来源的高风险事实不得通过 QA；
- 现有发布字段、发布预检和远端回读测试继续通过。

## 8. V1 实施记录

- 已新增角色化素材卡并在每次生成前冻结；其版本和哈希保存到 `articles.article_parts`。
- Brief 缓存键、大纲、正文、QA 与两次以内的局部修复都使用同一快照。
- 已保留发布器及远端格式；仅对齐规则中与实际 YAML 处理相矛盾的描述。
- 真实 AI 非发布干跑：主站样稿首稿因无来源安全表述被 QA 拦截；一次修复后添加允许的 FDA 来源和已批准产品链接，全部 QA 通过。

## 9. 安全试生成与排查

- 使用 `POST /api/v1/workflow/article-test` 进行文章效果测试；该接口只读站点资料并调用 AI，**不写 articles、keywords、tasks 或效果观察数据，也不发布到外站**。
- 试生成返回正文、QA、步骤和素材卡，可先人工检查再决定是否进入正式策略执行。
- 关键事件写入 `logs/seo-workbench.jsonl`：开始、SERP、素材卡、Brief、大纲、首稿 QA、局部修复、完成或拦截。日志不记录完整 Prompt、正文或密钥。

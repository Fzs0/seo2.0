# Strategy Policy v1 草案

状态：设计草案，尚未实施  
日期：2026-07-18（Asia/Shanghai）

## 1. 目标

让策略大脑在生成新写、更新、合并或暂缓建议前，能够读取相关历史，避免重复策略，并在统一观察期后评价效果。

本草案先锁定稳定语义，不把具体天数写死在数据库结构中。所有阈值通过版本化规则集管理；历史任务永久保留当时使用的规则版本。

## 2. 记忆分层

```text
事实记忆：站点知识、文章库存、主题覆盖、诊断、GSC / GA4、SERP
经历记忆：提出、批准、驳回、执行、失败和暂缓的策略任务
结果记忆：策略执行前后 7 / 14 / 28 / 56 / 90 天的效果
规则记忆：重复定义、冷却期、解锁条件和评价方法
```

数据库保存完整历史；每次规划只向 AI 提供当前站点和主题相关的紧凑上下文，不发送全量任务、正文或分析记录。

## 3. 策略身份

### 3.1 作用范围

```text
scope_key =
  site_id
  locale
  topic_cluster_id
  search_intent
  canonical_target_id
```

`scope_key` 用于识别正在操作同一内容资产的冲突策略。新写文章尚无目标页面时，以主题集群和搜索意图代替 `canonical_target_id`。

### 3.2 策略指纹

```text
strategy_fingerprint =
  scope_key
  action_type
  objective
  source_url_set_hash
```

- 同义词、词序和长尾表达不同，但搜索意图相同，仍属于同一范围。
- 同一页面的“优化标题 CTR”和“补充竞争缺失章节”可以是不同策略，但受同一页面观察锁约束。
- 同一搜索意图已经有可用页面时，不允许更换关键词再次生成新写策略。
- 合并策略只有来源 URL 集合、规范目标或目标意图发生变化，才视为新策略。

### 3.3 证据版本

```text
evidence_fingerprint =
  content_audit_id
  serp_snapshot_id
  analytics_window
  site_knowledge_version
  content_inventory_version
```

AI 换一种说法不构成新证据；只有结构化证据版本发生实质变化，才允许生成策略新版本。

## 4. 冷却规则

以下为 `strategy_policy_v1` 默认值，不是 Google 官方期限。

| 动作 | 默认冷却 | 规则 |
|---|---:|---|
| 待审核、排队、执行中 | 硬锁 | 终态前不生成重复或冲突策略 |
| 新写文章 | 同一意图永久防重复新写 | 对应页面存在时只能更新、合并或扩展子主题 |
| 更新旧文 | 28 天 | 观察期内不再次修改同一页面 |
| 合并、301、canonical 调整 | 56 天 | URL 结构变化采用更长观察期 |
| 人工驳回 | 14 天软冷却 | 到期不自动重提，必须有新证据 |
| 暂缓 | 每 14 天复查 | 不自动执行；最长 56 天强制重新评估 |
| 执行失败 | 不创建新策略 | 修复后重试原任务 |
| 主动停止 | 不创建新策略 | 等待人工恢复、取消或重新规划 |

冷却优先从 Google 首次抓取新版本的时间起算；尚未确认抓取时，任务保持 `awaiting_crawl`，临时以上线时间计算。

## 5. 新证据与解锁

### 5.1 立即解锁技术修复

- 404 / 5xx、错误 `noindex`、robots 阻断；
- canonical 指向错误页面；
- 发布接口失败或页面没有正确上线；
- 安全问题、人工处置或用户明确的业务变更。

技术证据只解锁技术修复，不能借机绕过内容策略冷却。

### 5.2 允许生成策略新版本

- 文章发布、删除、合并或规范页面变化；
- 新诊断发现实质质量问题或竞争差距变化；
- Top 10 中至少 30% 的结果类型或主搜索意图变化，并由间隔至少 7 天的两个 SERP 快照确认；
- 最近完整 28 天与前一完整 28 天相比，在至少 200 次展示的前提下变化达到 20%，连续两个自然周方向一致，且超过该页面历史正常波动的 2 倍；
- 产品、价格、法律、市场、语言或业务目标发生变化；
- 既定效果评估到期并确认未达到预期；
- 人工提供了新的业务证据。

这些百分比和样本阈值属于产品默认值，后续可通过新规则版本调整。

### 5.3 不能解锁

- 单日排名波动；
- 最近 2 至 3 天尚未稳定的数据；
- 页面尚未被重新抓取；
- 仅更换同义关键词或 AI 表述；
- GA4 与 Search Console 数字不完全一致；
- 算法更新、季节性或站点故障造成的暂时波动。

算法更新或其他外部事件应把观察状态标记为 `contaminated`，而不是直接认定旧策略失败。

## 6. 效果评估

| 时间点 | 检查内容 | 结论权限 |
|---|---|---|
| T+0 | 页面、埋点、状态码、canonical、robots | 只判断部署是否成功 |
| T+3 | GSC / GA4 是否开始产生稳定数据 | 只做异常报警 |
| T+7 | 抓取、索引和 canonical | 只判断技术状态 |
| T+14 | 展示、点击、CTR 初步趋势 | 不允许再次修改 |
| T+28 | 第一轮正式效果评估 | 更新策略可形成初步结论 |
| T+56 | 低流量、合并和重大更新 | 形成主要结论 |
| T+90 | 新页面、低样本和站点级变化 | 形成长期结论 |

正式评价使用“修改后完整 28 天”与“修改前完整 28 天”比较：

- 排除最近未稳定的 3 天；
- 按周聚合，避免工作日和周末错位；
- 季节性业务增加去年同期比较；
- 观察期内再次修改页面，旧评估标记为 `contaminated`；
- 展示、点击、CTR、自然流量和转化为主指标，平均排名只作辅助；
- 样本不足时标记 `inconclusive`，不能判定失败。

最终评价状态固定为：

```text
winner / neutral / loser / inconclusive / contaminated
```

## 7. 任务记录要求

策略与执行记录至少需要保存：

```text
scope_key
strategy_fingerprint
evidence_fingerprint
policy_version
cooldown_until
evaluation_due_at
unlock_conditions
supersedes_strategy_id
site_id / keyword_id / topic_cluster_id / target_post_id
action_type / objective / priority / confidence
evidence_refs / expected_outcome
status / started_at / finished_at / result / error
```

生成、驳回、失败、暂缓和执行成功都必须留存。失败任务应重试原记录，策略新版本通过 `supersedes_strategy_id` 关联旧策略，不能覆盖历史。

## 8. 业务范围

策略规划单位是业务，不是单个站点，也不是站点技术类型。

站点需要明确：

```text
business_id       属于哪个业务
strategy_enabled  是否参与该业务的策略规划
```

- 每次规划分析当前 `business_id` 下全部 `strategy_enabled=true` 的站点；
- `shopify`、`blog`、`wp` 只描述连接器或站点技术类型，不能用于判断业务归属；
- 当前 Shopify 站不属于当前业务，应通过业务归属或策略开关排除，而不是永久排除所有 Shopify 站；
- 没有可靠机会的站点允许输出“本轮无需行动”，不能为了覆盖率强行生成策略。

## 9. 业务分析、策略池与行动计划

规划链路拆成四层：

```text
业务分析批次
  → 完整策略候选池
  → 今日行动计划
  → 具体执行任务
```

### 9.1 业务分析批次

分析当前业务全部启用站点，不设置“最多 4 条”的分析上限。保存站点内容覆盖、机会、阻塞和数据完整性摘要。

### 9.2 完整策略候选池

保存经过重复、冷却和证据检查后的全部候选。P0 / P1 / P2 是候选优先级；Hold 单独进入阻塞列表，不计入可执行动作数量。

### 9.3 今日行动计划

“4”只表示当前阶段的默认动作预算，不限制 AI 分析范围，也不是必须凑满的目标。

```text
daily_action_budget = 人工配置的当前业务动作上限
per_site_soft_cap = 2
```

- 用户可以调整总动作数和各站点配额；
- 用户可以锁定、排除候选，再让 AI 填充剩余名额；
- 只有 2 个可靠机会时执行 2 个；没有可靠机会时允许执行 0 个；
- P0 可建议人工突破单站软上限，但不能绕过风险授权；
- 未入选候选保留在策略池，下一轮重新验证后继续参与排序。

### 9.4 后续自主配额

效果数据成熟后，AI 在业务预算和安全边界内，根据可执行机会、队列容量、站点观察期、失败率、成本、风险和历史成功率自动决定当日动作数量与站点分配。

### 9.5 关键词来源分流、页面簇准备与站点分配（Strategy Builder 本地校验已实现）

此前计划在“生成今日策略”前自动分析并分配全部未分配关键词。该顺序已经废止：它会把几万行关键词变成每日前置任务，并在发现真实内容机会之前制造大量站点分配和 Hold 噪音。

统一流程按来源已有证据分流，具体版本见 `docs/KEYWORD_IMPORT_PIPELINE_V1.md`。Strategy Builder 已有 `Topic / Page / Page type / TOP 10`，可以直接进入本地页面簇校验；Topic 列表、基础关键词和 GSC 排名词分别先形成暂定主题或按真实排名 URL 归组，再补 SERP 证据。不能把 Strategy Builder 专用规则套到只有 Keyword 的基础文件。

Strategy Builder 分支：

```text
导入 Keywords sheet
  → 本地规则筛选、去重、市场和语种检查
  → 保留 Topic / Page / Page type
  → 用文件内 TOP 10 竞争 URL 校验 Page 搜索簇
  → AI 按页面簇补充意图、页面类型和内容方向
  → 按页面簇分配目标站点
  → 关联已有文章库存
  → 生成新写、更新/扩展或关键词蚕食 Hold 候选
```

字段语义：`Topic` 是站点内容体系中的大主题；`Page` 是更接近单个目标页面的搜索簇；`Keyword` 是页面簇中的主词或辅助词；`Page type` 表示 Pillar/Sub page。一个大主题可以包含多个页面簇，不能把整个 Topic 强行写成一篇文章。

约束：

- `Keywords` sheet 是正式导入源，`Pages` sheet 仅作透视展示；
- Semrush `Page` 是待验证的初始簇，不能被当前通用词形聚类静默覆盖；
- 页面簇校验 V1 使用 TOP 7 共享 3 个 URL 或 TOP 10 共享 4 个 URL 作为强关系，TOP 10 共享 3 个 URL 作为可接受关系；输出 `validated / provisional / bridge_review / split_review`；
- `validated` 和 `provisional` 可进入下一阶段按簇 AI，`bridge_review` 和 `split_review` 先人工复核或补查；所有状态均保留原始簇，不自动删除或拆分；
- 优先复用导出文件中的 TOP 10 URL，只对过期、缺失或边界不清的页面簇调用 SerpApi；
- AI 以页面簇为单位命名、判断意图和分配站点，不逐行给几万条关键词分站；
- 页面簇与站点的匹配必须受市场、语种、站点知识和现有文章库存约束；无法确认时进入 Hold；
- 站点配额只能从真实候选中选择，不能为了填满配额强行分配主题；
- 已有文章更新继续由全站诊断独立产生，不得被关键词或页面簇导入阻塞；
- GSC、SERP 和竞争差距后续仍可产生不依赖 Semrush 表的新机会。

## 10. 优先级、风险和工作量

三者必须分开保存：

```text
priority       商业价值和紧急程度
risk_level     执行风险
effort         预计工作量
approval_mode  所需授权方式
```

| 风险 | 典型动作 | 默认权限 |
|---|---|---|
| L0 | 扫描、诊断、竞争分析、策略排序 | AI 自动完成 |
| L1 | 生成草稿、Meta 和内链建议 | AI 自动准备，不直接写线上 |
| L2 | 发布新文章、大幅更新单篇正文 | 前期人工批量审核后执行 |
| L3 | 删除、合并、301、slug、canonical、noindex、跨站调整 | 始终逐条人工确认并准备回滚 |

前期所有外站写入至少经过一次人工批准。后续只逐步开放低风险动作；L3 不进入无人值守自动执行。

出现以下任一条件时至少升级为 L3：修改 URL / slug / canonical / 索引状态，删除或重定向页面，一次影响多篇文章，跨站移动内容，改变主关键词或搜索意图，修改业务归属或站点知识边界，或者大规模批量发布。

## 11. 执行前重验证与人工反馈

候选进入执行前必须重新检查：

```text
目标文章仍然存在
远端 ID 和 canonical 未变化
没有冲突任务正在执行
没有进入新的冷却期
证据没有过期
站点仍属于当前业务且允许策略执行
```

验证失败时返回候选池或标记阻塞，不能使用旧快照继续写入线上。

同时保存 AI 推荐、人工最终配额、锁定、排除、驳回原因和实际执行结果。单次人工调整不自动形成永久偏好；多次一致选择和效果结果才能沉淀为业务偏好。

## 12. 自治阶段与终极看板

### 阶段 A：人工配置动作

AI 分析全部业务站点并生成完整候选池；人工设置总动作数量、站点配额并选择执行。

### 阶段 B：AI 推荐行动计划

AI 推荐动作数量和站点分配；人工一次确认整个低中风险行动计划，高风险动作逐条确认。

### 阶段 C：受约束自主执行

AI 在预算、风险、冷却和权限边界内自主决定每天做什么、做多少；L3 继续等待人工。允许 AI 在没有可靠机会时选择 0 个动作。

数据看板至少展示：

```text
分析了哪些业务站点
AI 推荐与实际执行了什么
为什么选择这些动作
动作成本、风险和执行状态
winner / neutral / loser / inconclusive / contaminated
各站点和各动作类型的历史成功率
观察中、冷却中、暂缓和需要人工处理的事项
下一轮预计动作
```

终极目标是人负责业务目标、预算、风险边界和例外，AI 负责日常分析、规划、低中风险执行及效果复盘。

## 13. AI 上下文控制

每次策略规划只构造以下上下文包：

```text
站点知识摘要
主题覆盖与相关现有页面
当前候选及最新诊断
最多 5 条相关策略历史
当前冷却和解锁状态
相似策略效果摘要
业务约束和今日产能
```

站点知识的定位与 `in_scope_topics` 只能由站点配置、已发布内容、产品和索引扫描推导。候选或已分配关键词只能与站点知识对照，不能作为扩张站点范围的证据，避免“先错分、再自证”的循环。

先读取摘要，只有候选进入最终比较时才展开原始诊断和竞争证据。原始记录始终保留在数据库中，因此摘要不会成为唯一事实来源。

## 14. 版本管理

- 初版规则名：`strategy_policy_v1`；
- 任务保存 `policy_version` 和当时计算出的时间、阈值及解锁条件；
- 新版本只影响新策略，不回写或篡改历史策略；
- 稳定字段进入数据库，14 / 28 / 56 / 90 天及 20% / 200 次展示等阈值放入版本化配置。

## 15. 当前边界

本文件仍是治理设计草案。业务级规划范围、完整候选池、人工动作预算、站点配额和今日行动计划已完成第一阶段并在本地真实验证。Semrush Strategy Builder 专用适配、只读预览、人工确认写入、页面簇本地边界校验、按簇 AI 分站及同站文章库存关联已实现；120 个可用簇已分析，96 个已分站簇已完成库存候选只读预演，39 个复核簇保持未分析。稳定策略身份、策略/证据指纹、规则版本、重复与 28 天更新冷却、执行瞬间重验证、T+0 基线、发布远端回读及 T+7/14/28/56/90 效果观察 V1 已实现并通过本地自动化测试，但尚未由当前后端进程和真实时间窗口验证。页面手动验收、其他关键词来源分支、风险授权、新证据提前解锁、策略记忆检索和 AI 历史上下文注入仍未实现。

实施前需要把本草案拆为最小顺序：

1. 为站点补齐业务归属和策略开关（已完成）；
2. 建立业务分析批次、完整候选池、今日行动计划和人工配额（第一阶段已完成）；
3. 实现 Semrush Strategy Builder 专用导入、页面簇预览、基础异常校验、人工确认写入和 TOP 10 边界校验（已完成本地验证，待页面验收）；
4. 实现页面簇级 AI、按簇分站、文章库存关联及新写/更新/蚕食 Hold 候选（已完成本地只读预演，待页面验收）；
5. 在第一批新执行前增加稳定策略身份、执行前基线和效果记录（已实现，待真实策略验收）；

# AI 主导 SEO 自主运营方案总结

- 日期：2026-07-31
- 状态：正式 AI 主链路已实现并通过代码/PG17 门禁；地区化实时搜索采集暂缓
- 适用范围：SEO 2.0 全部业务、主站、博客站及未来新增流量站点
- 核心模式：AI 为主、后端保障、人工处理例外
- 配套目标：`docs/AI_LED_SEO_STRATEGY_GOAL_2026-07-31.md`

## 0. 当前实现结论

新运行入口已经收口为：

```text
Scope/Evidence
→ AI Research Portfolio
→ AI Proposed Actions
→ Backend Safety Review
→ Zero Action Review
→ Formal Plan
→ Unified Action
→ Readback/Observation
```

旧 `run-local-options` 路由已经删除，候选池只保留历史只读查询；新 Research、
Strategy 和 Action 不接受 `candidate_id`。安全容量只负责将溢出动作保存为
Deferred，每个站点当前波次最多一个远程写 Action。当前产品决定暂缓通过
Computer Use 或其他交互方式采集地区化实时 SERP/SEMrush；在目标地区、语言、
设备和采集网络明确前，不把不同地区的结果混用。本轮仍可使用 GSC、GA4、Site API、
已保存的本地化快照、权威资料和固定 Evidence Adapter。

## 1. 背景

2026-07-31 的组合策略运行覆盖了 6 个业务、12 个活动流量站点，其中 9 个启用
策略的站点进入正式 Strategy Run，但最终结果为：

- `new_article`：0；
- `update_article`：0；
- `on_page_fix`：0；
- 统一 Action：0；
- 远程内容写入：0；
- 正式 Run：全部为 Hold。

这不是后端异常、动作额度不足或候选池为空造成的。最新 4 个正式 Run 均为
`action_budget=4`、`exception_count=0`，后端完整执行了调用方提交的决策。

## 2. 本次没有生成文章的直接根因

### 2.1 决策脚本预先缩小了动作空间

本次临时运行脚本的 `New-Decision` 只允许：

```text
hold
configuration_repair
```

因此 `new_article`、`update_article` 和 `on_page_fix` 在提交后端以前就已经不可能
出现。后端只保存和执行收到的选项，没有主动拒绝一批文章动作。

### 2.2 冷却和在途任务影响范围过宽

运行决策把“站点最近发布过内容”“站点存在观察任务”或“站点存在一个旧 Action”
近似当成了整站阻塞条件。

正确规则应当是：

- 文章更新冷却只匹配同一个规范 URL；
- 新文章冲突只匹配同一站点内高度重叠的搜索意图；
- 旧 Action 只阻止相同目标、相同 URL 或相同意图；
- 同一站点的其他 URL、其他搜索意图和其他动作类型仍可研究和执行；
- 只有连接器故障、远端状态不确定、错误站点风险等 P0/P1 问题才能整站阻塞。

### 2.3 研究不足被误写成“没有机会”

本轮多站点组合只执行了一次 `nic salt strength chart` SERP 查询。部分站点仅因
GSC/GA4 数据量少就进入 Hold，没有继续通过以下渠道补证：

- 对应语言、市场和站点定位的实时 SERP；
- 当前商品、分类和文章库存；
- 公共搜索回退；
- 现有页面结构、内容缺口和用户需求；
- 同站历史执行效果。

“分析数据少”表示需要扩大研究，不能直接证明“没有用户需求”。

### 2.4 全量 Hold 缺少不可绕过的二次复审

当前链路允许调用方直接提交全量 Hold。系统能够验证字段、站点归属和动作状态，
但没有验证：

- 五类动作是否在本轮真正开放；
- 是否错误使用了整站冷却；
- 是否完成了逐站研究；
- 是否存在被遗漏的不同搜索意图；
- 是否因旧 Action 连带阻止了无关目标；
- 是否因安全上限丢弃了合格动作。

## 3. 已确认的运行原则

### 3.1 AI 是运营主体

AI 负责：

1. 发现全部业务和站点；
2. 读取产品、分类、文章、页面、GSC、GA4 和历史效果；
3. 挖掘用户需求并进行实时 SERP/公开搜索研究；
4. 为每个站点构建多个有实质差异的可选方向；
5. 自主决定新写、更新、On-page、Hold 或配置修复；
6. 决定优先级、执行波次和延后条件；
7. 生成正文、SEO 字段、封面图、内容图和 Alt；
8. 完成发布前 QA；
9. 编排正式 Action 执行；
10. 检查远程回读和公开页面；
11. 在 7/14/28/56/90 天分析效果并改进后续策略。

### 3.2 后端是安全执行保障

后端负责：

- 验证 business/site/目标对象身份；
- 验证 Site Capabilities 和字段白名单；
- 精确检查同 URL/同意图冷却和在途冲突；
- 验证禁写字段、高风险事实来源和远端状态；
- 保存 Strategy、Plan、Action、Execution 和 Observation 血缘；
- 提供幂等、租约、心跳、超时恢复和旧 Token 拒绝；
- 根据连接器选择正确 Adapter；
- 执行远端写入并独立回读；
- 返回稳定异常码和阻塞原因；
- 保存全部 `execute_now`、`deferred`、`hold` 和
  `configuration_repair` 结果。

后端不得：

- 替 AI 指定关键词或选题；
- 用固定分数重新选择主题；
- 让关键词词库或旧候选自动创建 Action；
- 因单个观察任务或旧 Action 阻塞整个站点；
- 静默删除合格的延后动作；
- 把一个不安全动作自动替换成另一个主题。

### 3.3 人工只处理例外

人工负责：

- 下达业务目标和范围；
- 设置禁止事项和品牌边界；
- 首次接入新站点时确认定位；
- 审批医疗、法规、尼古丁等高风险内容；
- 审批大规模修改或重大品牌方向变化；
- 处理 AI 无法从现有证据判断的真实业务选择；
- 查看数据看板、异常和效果报告。

低风险内容、基础 SEO 字段、媒体、发布、回读和观察应逐步交给 AI 自动完成。

## 4. 候选池和关键词库的最终定位

### 4.1 候选池退出新策略链路

候选池不再参与任何新策略的：

- 研究；
- 排名；
- 选择；
- 授权；
- Formal Plan 创建；
- Action 创建；
- 执行调度。

新 Run 不再读取或写入候选池，`candidate_id` 不再是正式策略字段或可选研究来源。
历史候选数据暂时只读保留，用于审计旧 Run、旧 Action 和旧日志；确认旧引用全部
解除后，再删除候选池相关业务逻辑。不得直接删除历史数据库记录。

### 4.2 关键词库只作为可选研究材料

历史关键词库可保留，因为其中由 Semrush 等工具导出的数据仍能帮助 AI 理解：

- 主题和用户表达；
- 需求修饰词；
- 历史搜索方向；
- 可能的市场和语言差异。

但关键词库：

- 可以完全不读取；
- 不能直接选择页面或动作；
- 不能创建 Strategy 或 Action；
- 不能因记录为空而阻止 AI 研究；
- 不能以搜索量、KD 或旧状态覆盖当前 SERP、产品和分析证据。

### 4.3 SEMrush 和未来多数据源

SEMrush 不属于候选池，也不等于数据库中的历史关键词库。用户明确下达相关任务后，
AI 可以通过 Computer Use 使用当前 Windows 中已经登录的 SEMrush 会话，查看或导出：

- Domain Overview；
- Organic Research 和自然排名；
- 关键词、URL、国家/地区、设备和时间趋势；
- 竞争对手和关键词差距；
- SERP Features、排名变化和估算流量；
- 与当前策略直接相关的其他研究数据。

SEMrush 数据属于第三方估算和竞争研究证据，不能：

- 证明本站真实点击、会话或转化；
- 证明商品参数、库存、价格或安全事实；
- 单独授权新建、更新或 On-page Action；
- 因搜索量、KD 或流量估算较高而覆盖 AI 的当前综合判断；
- 重新形成候选池。

每次 GUI 调研必须记录：

- `source_type=semrush_ui`；
- 查询域名、数据库国家/地区、语言、设备和时间范围；
- 报告名称和筛选条件；
- 抓取时间和数据新鲜度；
- 截图、导出文件或可复核证据路径；
- 登录失效、页面错误、额度限制或数据缺失；
- 该证据如何影响或没有影响最终决策。

未来新增 Ahrefs、Similarweb、Google Trends、Merchant Center、社媒平台或其他授权工具
时，均通过相同的 Evidence Source Interface 接入，不在 AI 决策主流程中增加平台专属
分支。

### 4.4 多数据源用途和冲突处理

不同来源回答不同问题：

| 问题 | 首选证据 | 其他参考 |
| --- | --- | --- |
| 商品、分类和页面事实 | 当前站点/产品/分类 API | 公开页面回读 |
| 本站真实搜索展示、点击和查询 | GSC | SEMrush 排名和流量估算 |
| 本站真实用户行为 | GA4 | 其他已验证分析平台 |
| 当前搜索意图和 SERP 页面类型 | 实时 SERP/公开搜索 | SEMrush 关键词和竞争页面 |
| 竞争对手、关键词差距和市场估算 | SEMrush 等第三方工具 | 关键词库、公开搜索 |
| 历史策略是否有效 | Action、Effect、Observation | GSC、GA4、公开页面 |

发生冲突时，AI 不做简单多数投票，而应：

1. 比较数据定义、时间窗口、国家/地区、设备、粒度和新鲜度；
2. 优先使用最接近待回答问题的第一方来源；
3. 把第三方工具标记为估算，不伪装成本站真实结果；
4. 无法解释的冲突进入补证或 Deferred；
5. 在日志中保留冲突、选择理由和不确定性。

## 5. 选定的正式方案

采用“AI 自主决策 + 后端硬门禁”的混合方案。

正式 Seam 位于：

```text
AI 研究并提交 Proposed Actions
                ↓
后端验证安全、能力、身份、冲突和执行容量
```

AI 决定“做什么、为什么做、先做什么、做多少”；后端只判断“这个具体动作能否
安全、准确、可恢复地执行”。后端可以因明确硬门禁将动作降级为 Deferred、Hold
或 Configuration Repair，但不能重新选题。

## 6. 目标流程

```text
发现全部业务及流量站点
  → 刷新站点、商品、文章、页面、GSC、GA4 和历史效果
  → AI 按需通过 Computer Use 获取 SEMrush 等外部研究证据
  → AI 逐站研究当前需求
  → AI 形成多个有实质差异的 Run-local 方向
  → AI 选择 new/update/on-page/hold/configuration repair
  → 保存 Research Portfolio 与 Proposed Actions
  → 后端精确检查目标身份、能力、风险、冷却和在途冲突
  → 保存 execute_now/deferred/hold/configuration_repair
  → 若 execute_now + deferred = 0，进入 Zero Action Review
  → 必要时要求 AI 通过第二证据通道补充研究
  → Formal Plan
  → Unified Action
  → preview
  → approve
  → execute
  → independent readback
  → public verification
  → observation
  → AI 在检查点分析效果并更新后续策略
```

## 7. Zero Action Review

当整个调用范围内：

```text
execute_now = 0
deferred = 0
```

Run 不得直接收口，必须复核：

1. 每个非硬阻塞站点是否研究了足够的不同意图；
2. Hold 是否包含当前证据、稳定原因码和解锁条件；
3. 冷却是否精确命中同 URL 或同意图；
4. 旧 Action 是否确实与新动作冲突；
5. 是否只因 GSC/GA4 数据少就停止；
6. 是否使用了对应语言和市场的 SERP 或公开搜索；
7. 五类动作是否真实开放；
8. 是否有合格动作被安全上限丢弃；
9. `configuration_repair` 是否被错误降成普通 Hold。

研究不足时返回 `research_revision_required`，由 AI 补充第二轮研究。证据完整且确实
没有合格方向时，允许 `all_hold_review_passed`。Zero Action Review 不得强制制造
文章，也不得放松权限、医疗、法规、远端不确定性等硬门禁。

## 8. 动作容量和调度

`action_budget` 继续保留，但只作为 `safety_action_ceiling`：

```text
10 个合格动作，当前安全容量为 3
→ 3 个 execute_now
→ 7 个 deferred
→ 0 个丢失或降级为 Hold
```

正常选题不使用固定动作数量；每站最多一个正在进行的远程写入，但完成干净回读后
可以进入下一波。不同动作类型的成本和风险分别判断。

## 9. 原问题与当前状态

1. 动作枚举预先缩小：已由五类动作完整评估合同阻断。
2. Research Portfolio 和 Proposed Actions：已建立正式、幂等、逐站覆盖接口。
3. Zero Action Review：已接入正式 Run，支持补证、合理全量 Hold 和连续停滞异常。
4. Configuration Repair 丢型：已修复并有 PostgreSQL 17 回归。
5. `strategy_enabled=false` 活动站点遗漏：已保留为 Configuration Repair。
6. 候选池旧入口：新写和运行入口已退役，历史查询只读保留。
7. 全量 Hold 研究质量：现在检查第二证据通道、五类动作评估和站点级证据。
8. 外部工具来源合同：通用 Evidence Adapter 已实现；地区化实时 GUI 采集按产品
   决定暂缓，恢复前必须先明确地区、语言、设备和采集网络。

## 10. 实施顺序

### 阶段一：立即止血

- 删除脚本中的两类动作限制；
- 生成结构化 `decision-manifest.json`；
- 增加逐站研究、冷却作用域和全量 Hold 预检；
- 把预检接入日志验证器；
- 新日志禁止再把候选池列为研究来源。
- 增加通用 Evidence Source 记录，支持 `semrush_ui`、实时 SERP、GSC、GA4 和未来
  授权来源；
- Computer Use 调研失败时记录失败并按证据策略降级，不把 GUI 可用性变成全局阻塞。

### 阶段二：后端正式收口

- AI 通过正式 Interface 提交 Research Portfolio 和 Proposed Actions；
- 后端只执行硬门禁、精确冲突和调度验证；
- 增加 Zero Action Review；
- 保存所有延后动作；
- 修复 Configuration Repair 持久化；
- 让全部活动流量站点进入覆盖矩阵；
- 正式 Action 只接受当前 Run、Plan 和已选择策略的完整血缘。

### 阶段三：影子、审批和低风险自动执行

- 影子运行：对比新旧决策，不创建远程 Action；
- 人工审批期：验证 AI 策略与后端门禁是否准确；
- 低风险自动执行：基础文章、媒体和 SEO 字段自动发布；
- 高风险内容继续人工审批；
- 新业务站通过能力、Adapter、回读和覆盖测试后加入同一链路。

### 阶段四：删除旧链路

- 停止新候选池读写；
- 删除候选池到 Strategy/Action 的旧入口；
- 删除能够直接提交预先写死 Hold 的临时旁路；
- 删除不再需要的旧评分和旧调度逻辑；
- 保留历史审计数据和兼容读取，直到旧关系完成归档。

## 11. 不在本目标中的事项

- 不要求改造前端；前端继续作为只读数据看板。
- 不要求每天或每站强制发布文章。
- 不放松受保护字段和高风险内容门禁。
- 不允许跨业务制造外链。
- 不把关键词库替换成新的固定选题系统。
- 不删除历史候选、Run、Action 或效果记录。

## 12. 最终结论

本次“全部 Hold”首先是执行决策质量问题，而不是后端发布能力问题。正式修复不能
只扩大动作数量，也不能把选题重新交给固定后端评分。最终链路必须是：

```text
AI 研究、决策、生成、编排、验收和学习
              ↓
后端验证、持久化、执行、回读和追踪
              ↓
人工只处理高风险和业务例外
```

候选池退出新策略链路，关键词库保留为 AI 可忽略的研究素材。只有这一模式同时满足
AI 自主性、执行安全性、未来扩站能力和完整可追踪性。

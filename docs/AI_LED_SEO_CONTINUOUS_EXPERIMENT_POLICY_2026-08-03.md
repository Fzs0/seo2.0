# AI 主导 SEO 持续实验与 Hold 收敛规则

- 日期：2026-08-03
- 状态：代码已实现并通过本地及 PostgreSQL 17 验收；待下一次真实策略运行前向验证
- 适用范围：SEO 2.0 全部业务、主站、博客站及未来新增站点
- 目标使用者：Codex、后端开发 Agent、验收 Agent
- 关联文档：`docs/AI_LED_SEO_STRATEGY_GOAL_2026-07-31.md`
- 规则优先级：本文件自 2026-08-03 起覆盖旧文档中允许普通证据完整全量 Hold、
  `all_hold_review_passed` 和 `STRATEGY_STAGNATION` 的旧规则。

## 1. 背景

当前策略链路容易把“证据不足”“某个页面正在冷却”或“某个主题正在观察”解释为
整个站点不应行动，最终产生大量 Hold。

这会形成一个无法自我改善的循环：

```text
要求已有充分证据
→ 因证据不足而不执行
→ 没有新的策略动作
→ 无法产生新的效果数据
→ 下一轮仍然证据不足
→ 继续 Hold
```

SEO 2.0 现阶段需要通过安全、可验证的小规模实验积累自身策略数据。只要不会危害
站点，就不应因为信心一般或第一方数据较少而停止新写、更新和 On-page 优化。

## 2. 核心产品决策

正式链路从：

> 证据充分才行动

调整为：

> 只要动作安全、符合站点定位、能够独立回读并持续追踪，就允许作为小规模实验执行。

系统的默认状态应当是持续发现和执行有学习价值的动作。Hold 是例外，不是常态。

动作预算是防止失控的安全保险，不是发布配额，也不得被当成正常选题数量上限。

## 3. 目标结果

每次策略运行应当做到：

1. 覆盖调用范围内的每个活动站点；
2. 研究该站点的文章、产品页、分类页和其他可优化页面；
3. 冷却或冲突只阻止相同 URL、相同内容资产或高度重叠的搜索意图；
4. 一个方向不可执行时，继续寻找不同页面、不同主题或不同动作类型；
5. 对安全但证据较弱的机会，以“探索性实验”执行，而不是直接拒绝；
6. 每个动作完成独立回读，并创建 7/14/28/56 天效果观察；
7. 根据成功、失败和样本不足的实际结果调整下一轮策略；
8. 只有真正的整站硬阻塞才能产生站点级 Hold。

对于没有整站硬阻塞的活动站点，一轮正式策略通常应产生至少一个有学习价值的动作，
但这不是强制发布配额。系统不得为了凑数制造重复、低质或不安全的内容。

## 4. Hold 的正确作用范围

### 4.1 URL 级 Hold

只暂停一个明确页面，适用于：

- 该页面刚刚更新，仍处于效果观察期；
- 相同页面存在 planned、queued、executing 或远端状态不确定的 Action；
- 页面正在等待独立回读、抓取、索引或 canonical 验证。

URL 级 Hold 不得阻止同站其他页面和不同搜索意图。

### 4.2 主题级 Hold

只暂停一个主题集群或搜索意图，适用于：

- 同一意图已有新文章或更新实验正在观察；
- 新方向会与现有页面形成明显内容重叠或关键词竞争；
- 医疗、法规或安全主题缺少必要的权威资料。

主题级 Hold 不得阻止同站其他主题，也不得自动升级为整站 Hold。

### 4.3 站点级 Hold

只有以下硬阻塞可以暂停整个站点：

- 无法确认 business、site 或远程目标身份，存在错站写入风险；
- 写入接口、认证、权限或连接器能力不可用；
- 远程写入结果不明确，继续写入可能产生重复内容；
- 公开页面无法完成必要回读，且无法确认实际发布状态；
- 站点发生大范围故障、数据损坏风险或异常批量发布；
- 所有安全写入能力被明确关闭；
- 用户明确暂停该站点。

以下情况不能单独构成站点级 Hold：

- GSC 数据少或为空；
- GA4 流量少；
- 关键词库没有记录；
- 候选池为空；
- 某一篇文章正在冷却；
- 某一个主题正在观察；
- 只研究的前两个方向没有通过；
- GA4 与 GSC 的数字不相等；
- AI 对机会只有中等或较低信心。

## 5. 持续探索规则

### 5.1 不以固定候选数量宣布机会耗尽

系统不得只检查“一个旧文方向和一个新文方向”就认定整个站点没有机会。

当首选方向被冷却或拒绝后，AI 应继续依次检查：

1. 其他已有文章是否需要更新；
2. 是否存在不同搜索意图的新文章机会；
3. 产品页的 Title、Description、正文、图片 Alt 和结构是否可优化；
4. 分类页是否缺少独立搜索定位和基础 SEO 元素；
5. 站内链接、内容结构和用户问题覆盖是否存在缺口；
6. 是否有能够安全执行的技术性 On-page 修复。

不设置固定的“至少研究几个候选”。AI 必须持续研究，直到找到安全动作，或能够证明
整个站点存在硬阻塞。日志应记录真正评估过的主要方向，不能用空泛描述代替研究。

### 5.2 证据等级只决定实验强度

机会按照证据强度分为：

| 等级 | 典型证据 | 默认处理 |
|---|---|---|
| 高 | GSC、GA4、SERP、站内数据相互支持 | 优先执行 |
| 中 | 两类证据支持，仍有不确定性 | 小规模执行并加强观察 |
| 低 | 第一方数据少，但用户需求、SERP 或产品事实能够支持 | 作为探索性实验执行 |
| 不安全 | 事实不可验证、明显重复、错站风险或远端状态不明 | 阻止或 Hold |

“低证据”不等于“无机会”。只有“不安全”才直接禁止执行。

### 5.3 动作类型可以切换

AI 不需要执着于最初选择的动作：

- 旧文章正在冷却，可以研究其他文章或新主题；
- 新文章会产生重叠，可以更新现有页面；
- 内容证据暂时不足，可以执行基础 On-page 优化；
- 产品页不适合修改，可以研究分类页或博客；
- 当前站点确实不可写，才进入配置修复或站点级 Hold。

动作切换必须由 AI 根据证据决定，后端不得自行替换主题或动作。

## 6. 安全红线

持续实验不代表无控制地发布。以下保护必须保留：

- 不在短时间内向同一站点批量发布十几篇低质量文章；
- 不连续修改仍在观察期内的同一个 URL；
- 不为同一搜索意图重复创建页面；
- 不虚构产品参数、医学效果、法规结论或权威来源；
- 不擅自修改 URL、slug、canonical、redirect、价格、库存、Variant、分类成员关系；
- 不绕过 business scope、Site Capabilities、字段白名单、审批和幂等门禁；
- 写入结果不明确时不得盲目重试；
- 每次远程写入必须独立回读；
- 回读不一致时必须创建异常，不得建立正向效果观察；
- 新平台或新写入能力首次开放时必须先进行受控小样本验证。

执行规模应由站点当前状态、写入能力、回读能力和观察容量共同决定，不使用固定文章数
作为日常 KPI。安全容量超出的合格动作应保存为 Deferred，不得丢弃或改成 Hold。

## 7. 正式决策流程

```text
发现全部活动站点
→ 刷新站点、产品、内容、GSC、GA4、SERP 和历史效果证据
→ 排除真正的整站硬阻塞
→ 研究多个不同 URL、主题和动作类型
→ 对每个方向执行精确的 URL/主题冷却与冲突检查
→ 选择安全且有学习价值的动作
→ 标记高/中/低证据等级
→ 形成正式 Strategy 和 Action
→ Preview / Approval / Execute
→ 独立回读
→ 创建 7/14/28/56 天 Observation
→ 根据效果生成下一轮策略
```

如果最终仍然没有执行动作，Zero Action Review 必须回答：

1. 是否存在真正的站点级硬阻塞；
2. 哪些 URL 被精确冷却；
3. 哪些主题因重叠或安全问题被阻止；
4. 是否检查了文章、产品、分类和 On-page 四类机会；
5. 为什么低证据方向不能作为探索性实验；
6. 明确的解锁条件和下一次复评时间是什么。

没有这些证据，不允许把 Run 结束为整站 Hold。

## 8. 策略数据与学习闭环

每次动作继续写入现有数据库中的正式对象，不建立旁路策略库：

```text
Strategy Run
→ Research Portfolio
→ Proposed Action
→ Formal Plan
→ Action / Execution
→ Readback
→ Effect / Observation
→ Strategy Learning
```

每个动作至少记录：

- 站点和目标身份；
- 新写、更新或 On-page 动作类型；
- 用户搜索意图；
- 使用的证据及其限制；
- 为什么选择该动作；
- 被放弃的主要替代方向；
- 执行前内容或 SEO 字段快照；
- 实际修改内容；
- 写入和回读结果；
- 观察指标和检查时间；
- 最终状态：exploring、promising、validated、inconclusive 或 failed；
- 下一轮策略应继续、扩大、调整还是停止。

其中：

- `exploring` 表示正在积累数据；
- `inconclusive` 表示样本不足，不代表策略失败；
- 成功策略可以扩展到相近页面或同类站点；
- 失败策略应记录失败条件，避免机械重复；
- 后续 AI 决策应优先使用实际执行结果，而不是只依赖历史关键词和静态规则。

## 10. 验收标准

完成实现后，至少验证以下场景：

1. 一个 URL 冷却时，同站不同 URL 仍可产生 Action；
2. 一个主题观察中，同站不同搜索意图仍可产生 Action；
3. GSC 为空但 SERP、产品和站内证据充分时，可以创建探索性动作；
4. 旧文不可更新时，AI 能继续研究新文、产品、分类和 On-page；
5. 低证据安全动作不会被自动改成 Hold；
6. 医疗或法规事实缺少权威来源时，只阻止相关主题；
7. 真正错站风险或远端状态不明时，可以整站 Hold；
8. 合格但超出当前安全容量的动作进入 Deferred；
9. 所有成功写入均有独立回读和 Observation；
10. Zero Action Review 不能只凭两个失败方向宣布整站机会耗尽；
11. 新增业务站后，无需新增站点专属决策规则即可遵循相同范围语义；
12. 日志和数据库能够还原“为什么行动、做了什么、结果如何、下一步如何调整”。

## 11. 非目标

本规则不要求：

- 每个站点每天固定发布文章；
- 为了产生数据而制造低质量内容；
- 取消 URL 或主题冷却；
- 放松医疗、法规、产品事实和远端写入安全要求；
- 绕过统一 Action、审批、幂等、回读和观察链路；
- 让后端替 AI 选择关键词、页面或文章主题；
- 恢复候选池对策略的控制。

最终目标不是“发布越多越好”，而是持续进行安全、可验证、有学习价值的 SEO 实验，
让系统依靠自身积累的策略效果数据逐步提高决策质量。
